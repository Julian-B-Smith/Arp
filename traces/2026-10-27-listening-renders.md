# listening-renders — the shipped core rendered to WAV / MIDI, and a page to listen, judge and report

- **Queue item:** T-007 (ROADMAP M3), the gate row "the human's playing sign-off is recorded here" (horde's note-processor bar section 6: the human's listening sign-off). Dispatch from the Arp lead session, 2026-10-27, on branch `m3/listening` (from `e00ab6a`). Working tree uncommitted; the only git operation was `git switch -c m3/listening`.
- **Why:** the sign-off has to be of the SHIPPED C++ core, not the lab twin. `tests/core/render.cpp` (target `arp_render`, linked to `arp_core`, no ARP_PLANTS) drives `Core` as horde would (prepare once at 44.1 kHz, blocks of 256, one settings snapshot per block, exact `rep` position, integer-sample input) through 18 scripted scenarios and writes WAV, MIDI and `manifest.json` into `build/listen/` (gitignored); `lab/listen.html` plays them with a piano roll, a three-way verdict, notes and a copyable summary.
- **Evidence consulted:** CLAUDE.md section Domain; spec/SPEC.md sections 1-6, 8, 9, 14 (restart adoption, once-guard, ties, latch, chord stage, triggers under restart bar/free); spec/params.json (labels, value_labels, units); spec/bank/starter.json; lab/patterns/broken-chord-stabs.json (transcribed into render.cpp as a `UserPattern`: picks 1,3,2,chord,1,4,chord+step 1,2); core/include/arp/core.h, types.h, pattern.h; tests/core/shipped_smoke.cpp, alloc_hook.*, CMakeLists.txt; tools/core_bench.sh; .claude/launch.json.
- **What was checked (evidence, not assumption):** each scenario's note/trigger stream was dumped from the manifest and read against its intent (order tour bars, restart chord/bar/free first-hit positions on the 3/16 grid, latch replace/add/toggle/pedal, chord stage with and without the +12 slot, quantize ties, transposition passes, trigger lanes). Two findings changed the scripts: (1) restart changes are adopted at the next evaluated step, so scenario 14's switch back to restart `chord` had to land before the new chord's press (else the first lane was 3, not 1); (2) trigger-only steps keep firing after the keys are released under restart `chord` once an anchor exists (SPEC 2.5), so scenario 14 ends soon after its last release.
- **Alternatives rejected:** a JSON parser in C++ for params.json labels (the page maps keys to labels instead; the manifest carries keys and values); parsing the user-pattern file in C++ (a transcription with a comment is smaller than a parser); one WAV gain per file (the brief asks for one common gain).
- **Additions beyond the brief:** an optional metronome click (flag, on in the restart scenario only: without a beat reference the restart difference is not audible); `--check` in the script (renders twice, compares byte for byte); the order and pattern tours are split in two parts each (16 bars at 120 bpm would run 32 s).
- **Verify:** `./verify fast` exit 0 (quiet on green), `.harness/last-verify.json` git `e00ab6a` (tree uncommitted); `bash tools/core_test.sh build` passes with `arp_render` compiled at -Wall -Wextra -Werror; `bash tools/render_listening.sh --check`: 18 scenarios PASS, 0 allocations inside process()/reset(), every NoteOn paired, two renders byte-identical (37 files). The page was loaded in headless Chrome from a local http.server (dark and light) and rendered all 18 cards; actual audio playback and the live playhead were NOT exercised headlessly.
- **Open questions:** (a) python's http.server does not serve HTTP Range requests, so seeking in the audio (clicking the roll) may be unreliable on the first click in some browsers until the file is buffered; (b) the first value in a "changed settings" chip is the initial one (e.g. the order tours list `Up` first even where it is replaced before the first step); (c) the synth is this file's, so judgments of timbre are not judgments of the core: only timing, order, count and level pattern are.
